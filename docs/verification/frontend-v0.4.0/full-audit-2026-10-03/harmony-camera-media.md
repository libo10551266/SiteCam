### HCM-01：旧照片结果能够落到新的拍摄请求

- **位置**：`CameraService.ets:349`、`:413–414`、`:539`；`Index.ets:612–614`。
- **触发**：拍摄 A 超过 15 秒超时后，用户重试拍摄 B；A 的 `photoAvailable` 较晚到达，或其 `getComponent()` 在 B 开始后才完成。关闭再打开相机时，已进入异步回调的旧会话也存在同类窗口。
- **根因**：`shoot()` 把当前完成/失败回调保存在共享的 `pending`/`failed` 字段；`photoAvailable` 在异步读取 JPEG 后直接清除当前超时并调用当前 `pending`，没有固定本次请求和会话的归属。`captureToken` 只保护 `onAccepted` 与定时器，不保护照片成功、读取失败或 `capture().catch()` 的 `reject()`。
- **结果**：A 的照片字节可以完成 B 的 Promise，并由页面用 B 已冻结的工程、时间和水印快照加工保存；旧请求的迟到错误也可以错误地拒绝 B。这里不是快照未冻结，而是照片字节与快照的请求归属可能错配。
- **最小修复**：建立拍摄请求和相机会话的共同归属，所有成功、失败、超时回调均校验归属并只完成一次。需要特别处理“超时后旧照片才返回”：API 12 可用的 `Photo` 只有 `main` 和 `release()`，不能凭空从照片对象获取 capture ID；在无法可靠关联输出时，超时后应先失效并释放/重建该输出，再允许下一次拍摄，并让回调闭包固定输出会话代次。单纯在 `photoAvailable` 开始时读取当前 `captureToken` 不能解决晚到事件。
- **定向验证**：固定两个可辨别场景与两套水印，延迟 A 到超时后再发 B；分别迟到成功和迟到失败，验证 B 不消费 A，也不会被 A 的错误取消。再覆盖旧回调已进入 `getComponent()` 时关闭/重开。成功回调仍须释放自己持有的图像资源。

### HCM-02：视频取消只作用于原生执行中的部分阶段

- **位置**：`VideoService.ets:10–29`；`video.cpp:246–247`；`Index.ets:463`。
- **触发**：用户在视频处理刚开始、读取媒体/视频信息或水印 PixelMap 时点取消，或应用切后台触发取消；也可在原生转码结束后、输出检查和数据库提交前取消。
- **根因**：ArkTS 服务将 `running` 置为真后进行多个 `await`，但不保存本次任务取消状态。`cancel()` 只修改原生全局标志，而 `transcode()` 开始时把它重置为 `false`。原生调用返回后也没有在检查/提交前重新判断本次任务是否已取消。
- **结果**：开始阶段收到的取消会被后续原生启动清除，任务继续占用编解码器并生成结果；收尾阶段的取消也可能继续提交为 READY。后台取消因此不能保证及时停止该次处理。
- **最小修复**：在 `VideoService` 内持久记录本次作业代次及取消状态，各异步阶段返回后和提交前检查。取消应关联当前作业，下一作业的初始化不能抹去当前作业已经收到的请求；原生运行期间保留原有取消检查。取消失败路径继续保留原片，并清理未提交输出。
- **定向验证**：分别在 `mediaById`、`inspectVideo`、`readPixelsToBuffer` 和输出检查处阻塞，取消后释放阻塞；确认前半段不再启动原生任务，提交前取消不写 READY，原片和重试入口保留。另跑一次正常处理，验证上一任务取消不污染下一任务。

### HCM-03：视频画面里的地址与导出索引不一致

- **位置**：`Index.ets:631–642`；`Models.ets:47–56`、`:185–200`；`ImageProcessor.ets:50–59`；`VideoService.ets:29`；`Store.ets:51–53`、`:78`；`ExportService.ets:40`。
- **触发**：拍摄含有效坐标或手工工程地址的视频，在同一次应用会话中导出。没有坐标、只有工程手工地址的视频，重启后也不能由当前回填条件补齐。
- **根因**：照片会调用 `hydrateMedia()` 从冻结快照写入纬度、经度、高程、定位精度、定位时间、定位状态与地址；新视频只设置工程、时间、snapshot、类型和路径，位置列仍为默认 `null`/`UNAVAILABLE`，地址仍为空。转码提交只更新处理结果列。数据库打开时的 `backfillSnapshots()` 仅对 `snapshot.fix` 存在的行回填，不能补齐无定位但有地址的行。
- **结果**：视频画面水印可显示正确地址，而 CSV 直接读 `item.addressText`、`latitude`、`longitude` 得到空值；有坐标的视频可能直到下次打开数据库才补齐，造成同一资料跨会话表现不同。
- **最小修复**：把照片已有的快照到媒体字段映射提取成共享函数，在新视频首次落库前调用。只用拍摄时快照，不能在处理完成时取新的位置或当前工程。修复旧数据时对地址和位置分别按快照回填，不以存在 GPS 为地址回填前提；保持列级处理结果更新，避免覆盖并发工程移动或问题编辑。
- **定向验证**：分别录制“新鲜定位+地址”和“无定位+工程手工地址”，同会话导出并比较 snapshot、数据库字段和 CSV；重启再导出，结果应一致。失败后重试的视频也应保留原拍摄元数据。

### HCM-04：视频末段的正常工作被 45 秒无进度判断中止

- **位置**：`video.cpp:74`、`:240`。
- **触发**：解码帧时间戳达到源时长的 95% 后，最后一段视频帧处理及编码排空耗时超过 45 秒。长视频或处理较慢的设备满足该条件时，即使持续产生帧，也会触发。
- **根因**：UI 进度被 `min(0.95, pts / duration)` 固定封顶；看门狗却只在这个进度数值发生变化时刷新活动时间。进入最后 5% 后，后续正常帧不会改变进度值。
- **结果**：正常工作的任务被当作停滞，抛出“视频处理超时，原片已保留”并删除成品，用户无法完成本来仍在推进的长视频处理。
- **最小修复**：分离 UI 进度与处理活动监测；以解码/编码有效帧或明确阶段进展刷新单调时钟，UI 可继续为音频和封装保留尾部进度。保留真实停滞的超时，不以简单增大固定秒数掩盖问题。
- **定向验证**：在最后 5% 持续推进帧但令该段总耗时超过 45 秒，任务应完成；再让解码和编码都停止产生有效进展，确认真实停滞仍触发超时并保留原片。没有必要并行打开多台模拟器。

### HCM-05：视频颜色转换没有使用源矩阵和范围

- **位置**：`video.cpp:44`、`:86`、`:234–239`，以及编码输出轨道配置。
- **触发**：原片/解码输出的实际矩阵或范围并非 BT.601 limited range，例如设备产生 BT.709 或 full range 的 SDR 视频。本轮没有采集设备视频，因此不据此断言所有当前设备均偏色。
- **根因**：着色器固定减去 `16/255` 并使用 `1.164/1.596/0.392/0.813/2.017` 系数；解码格式回调只处理尺寸跨距和像素格式，未按实际范围与矩阵调整转换。新建编码格式只设置编码、尺寸、像素格式、码率和帧率，未形成与实际变换一致的色彩元数据。NV12 只规定像素排列，不能据此固定色彩矩阵和范围。
- **结果**：满足上述输入条件时，加水印后的无水印区域也可能改变亮度、黑白层次或颜色；现有只抽取水印区域比对的检查不能排除此问题。
- **最小修复**：读取源轨道与实际解码输出的范围、矩阵等色彩信息，选择对应转换并向编码/封装传递与输出一致的元数据。先保持当前支持输入的 SDR 色彩正确；不要借修复扩展成未经要求的 HDR 新功能。
- **定向验证**：同设备录制带灰阶、黑白和饱和色块的视频，读取实际颜色标记，比较原片与成品的未叠加区域。覆盖实际支持的 BT.601/709 和范围组合；需要设备及解码后图像比较，不能仅凭尺寸、时长和播放成功判定通过。

## 需设备能力确认的候选，不计入新增 5 条

**HCM-C01：录像配置选择未考虑 profile 的最小帧率。** `CameraService.ets:341–346` 只按像素面积接近 1080p 排序，随后设置 `videoFrameRate = min(30, profile.frameRateRange.max)`，不读 `min`。如果排首位的档位只有 60 fps，则录像输出采用该档位，AVRecorder 却配置 30 fps。源码存在配置不一致，但当前设备会拒绝、降帧还是接受，尚无本轮能力集和录制结果证明，因此不列为已复现录像故障。

后续只需读取实际能力集并核对选中档位，在该设备录制一段即可；若证实受影响，最小调整是按目标帧率筛选真实支持的档位，并保持相机输出与录制器配置一致。官方录像指导要求选择 `frameRateRange` 满足业务需求的输出配置，见 [OpenHarmony 相机录像](https://gitcode.com/openharmony/docs/blob/OpenHarmony-6.0-Release/zh-cn/application-dev/media/camera/camera-recording.md)。

## 对已有 HAR-S14 的补充，不重复编号

`CameraService.open()` 在创建并打开相机输入后逐项创建输出、录制器、会话，但整个获取过程没有失败清理边界（`:336–354`）。页面正常照片相机打开失败时的 catch 只更新就绪标志和消息（`Index.ets:584–588`），不会立即调用 `close()`。例如输入已经打开后，预览配置或提交失败，已获取的资源可能保留到下次重试/离开/后台关闭。录像启动分支已经有显式 close，不能据此把全部路径都称为无清理。

此外，`foregroundChanged()` 的后台分支在等待声音挂起和方向恢复后继续关闭相机（`Index.ets:450–463`），未在这些等待后再次确认仍是同一次后台事件；快速后台再前台时，旧关闭流程可能与新打开流程交错。应在原 HAR-S14 的串行生命周期所有权和失效检查修复中一并处理，并让部分获取失败只清理自己拥有的会话资源。

## 已核实存在的保护，修复时应保留

- 拍照前冻结工程、设置、水印、位置和方向；拍摄入口重新读取工程锁定状态。照片落库失败时删除新成品；这不能替代 HCM-01 的请求归属检查。
- 照片加工和编辑通过工作任务执行；输入快照和配方序列化，照片字节不使用会转移并清空原输入的传输列表。图片编码写入循环处理短写，并在失败时清理输出、释放图像/编码对象。
- 编辑保存固定媒体 ID、配方和修订号；旧任务结果可被丢弃，数据库提交前后区分新旧成品，旧编辑成品在新记录成功后再清理。
- 视频处理先重新读取媒体行和原片路径；成功结果按列更新，能保留并发工程移动或问题编辑；媒体已删除会使提交失败，而不是悄悄重建资料。
- 视频输出会重新解析并检查显示尺寸、旋转、时长容差及原片音轨是否保留；失败清理未提交成品，原片保留供重试。服务层和原生层都限制同时只执行一项转码。
- 原生视频路径处理 NV12 跨距、旋转、H.264 配置与样本形式；原片音轨通过解复用/复用保留。格式对象、文件、音频缓冲区和编解码/EGL 对象存在显式释放路径。这里未把释放代码存在等同于各种设备错误路径已运行通过。
- 快门音具有代次、挂起屏障、加载事件先注册、超时和资源释放路径；播放失败不导致照片失败。它与录像麦克风采集分离。
- 系统相册副本保存固定目标媒体和路径，并仅更新相册 URI 列，避免用旧详情对象覆盖其他编辑。

## 官方接口核对

本轮按项目最低兼容 API 12 核对安装 SDK 声明，不建议为修复直接依赖更高版本接口。

- `@ohos.multimedia.camera.d.ts:5592–5610`：`Photo` 有 `main` 和 `release()`，未提供 capture ID；`:6271–6305` 的开始/结束事件信息才含 capture ID。因此 HCM-01 不能直接假定照片回调能读到 ID。
- `native_avcodec_base.h:827–853`：范围、原色、传递特性和矩阵键从 API 10 提供；HCM-05 所需基础元数据不要求提高当前最低版本。
- `native_avbuffer_info.h:92–97` 的 `pts` 为微秒；`native_avcodec_base.h:1769–1783` 的 Surface 纳秒要求与 API 20 新增、当前未开启的 PTS 码率控制选项相关。本轮没有把两种契约混用而新增“全部时间戳单位错误”的结论；当前路径的实际输出时间轴仍需设备验证。
- [OpenHarmony 官方拍照示例](https://gitcode.com/openharmony/docs/blob/OpenHarmony-6.0-Release/zh-cn/application-dev/media/camera/camera-shooting.md)同样展示 `imageObj.release()`；没有仅凭 `Photo` 另有 `release()` 就把当前 `main.release()` 路径判为已经证明的资源泄漏。

SDK 根目录：`/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/`。ArkTS 声明位于 `ets/api/`，上述原生头文件位于 `native/sysroot/usr/include/multimedia/player_framework/`。

## 后续最小运行验证

本轮用户指出同时运行过多模拟器会使 Mac 变慢。后续由统一资源管理者安排一次只用一台实际目标设备或一个必要实例；本报告不自行启动验证环境。

1. 优先验证 HCM-01 的迟到成功/错误，以及 HCM-02 的各阶段取消；这两项直接影响资料归属和用户操作是否生效。
2. 使用同一小组视频验证有/无录音、四方向、当次元数据导出、失败重试和系统相册副本，记录源与成品的实际时长、画面方向、声音和播放结果。
3. 对确实支持的相机能力验证 HCM-C01，避免把未存在的档位当成已发生故障。
4. 复用现有 `VideoOutputChecks.ets` 做尺寸/时长/音轨与首中尾水印检查；该检查请求 320×240 抽帧并比较水印区域，不能替代声音试听、连续播放、HCM-05 色彩比较或 HCM-04 的长视频尾段验证。
5. HAR-S14 的部分打开失败与快速前后台交错，同原前端生命周期修复一起回归。镜头可用性、点击对焦实际落点、变焦回读、闪光/补光、快门音与录音干扰仍需真实硬件证据。

本轮没有新增测试文件或调用设备测试；已有检查的存在不作为通过记录。
